# OCI와 Windows 실행 대상 확인

JK의 hub와 worker는 서로 다른 호스트에서 실행할 수 있다. 예를 들어 OCI의
Linux 프로세스는 MCP·승인 서버를 담당하고 Windows PC는 프로젝트 명령을
실행한다. OS가 다르다는 이유로 연결을 차단하지 않는다.

## 시작 시 확인

- Windows 시작 스크립트는 실행 역할, 호스트, 플랫폼과 작업 폴더를 표시한다.
  `executor-only` 모드는 로컬 MCP·승인 서버를 시작하지 않는다.
- `JK_EXECUTOR_WORKSPACE` 또는 `-ExecutorWorkspace`를 명시했다면 해당 폴더가
  실제 디렉터리여야 한다. 잘못 지정한 경로를 일반 `Workspace`로 대체하지
  않는다. 값을 생략한 경우의 기본 작업 폴더 사용은 지원한다.
- Linux 시작 스크립트는 HTTP 서버 역할, 호스트, 플랫폼과 작업 폴더를
  표시한다. Linux라는 이유만으로 OCI 환경이라고 가정하지 않는다.
- Worker는 작업 폴더의 실제 경로를 확인하고 인증된 heartbeat 응답의 hub·worker
  식별 정보를 검증한 뒤 작업을 받는다. HTTP 응답이 성공했다는 사실만으로
  준비 완료로 판단하지 않는다.

연결 규약은 `protocolVersion`과 `execution-target-v1` 기능을 사용한다.
각 도구가 필요한 실행 기능도 확인한다. OS·아키텍처·앱 버전 설명과 연결 규약의
호환성은 구분하며, 양쪽 OS나 전체 소스 해시가 같아야 한다는 조건은 없다.

## 실행 대상 고정

프로젝트 실행 대상에는 다음 정보가 포함된다.

- 로컬/원격 구분
- 실행기 ID와 실행 중인 인스턴스 ID
- 실행 호스트의 실제 작업 폴더
- 사용자가 선택한 논리 프로젝트 ID
- worker의 실제 프로젝트 ID와 프로젝트 경로
- 연결 규약 버전

일반 원격 도구는 선택한 대상 정보를 서버에서 채워 전송한다. Broker는 현재
등록된 실행기와 프로젝트 매핑을 대조하고, worker는 실제 실행 전에 자신의
인스턴스와 프로젝트 경로를 다시 확인한다. 클라이언트가 보낸 임의 경로를
신뢰해 실행 위치를 정하지 않는다.

Windows로 지정한 프로젝트에서 Windows 실행기가 꺼졌거나 연결 정보가
오래되었거나 프로젝트 매핑이 사라졌다면 요청을 중단한다. 같은 이름의
프로젝트가 OCI에 있다는 이유로 거기서 대신 실행하지 않는다. 명시적인
로컬 경로 선택과 현재 호스트에서 관리하는 task workspace는 계속 지원한다.

## 승인을 기다리는 작업

승인 대기 중인 shell·명령 작업에도 실행 대상을 저장한다. 승인 후 재개할 때
일반 도구와 같은 라우팅 규칙을 적용하고, 저장했던 대상과 현재 대상을
대조한다.

실행 호스트, 프로젝트 경로 또는 필요한 실행기 인스턴스가 달라졌다면 이전
승인을 새 대상으로 옮겨 쓰지 않는다. 실행 대상을 확인한 뒤 새 요청과
승인이 필요하다. 대상 증거가 없는 과거 대기 작업도 현재 대상으로 조용히
전환하지 않는다.

## 업데이트와 운영 확인

새 연결 규약을 적용하려면 hub와 사용하는 worker 런타임을 함께 업데이트해야
한다. 이전 worker가 새 규약을 제공하지 못하면 연결 또는 실행을 차단하는
것이 의도한 동작이다. 대시보드가 제공하는 standalone Windows 실행기 경로도
같은 규약을 사용한다.

각 호스트에서 실제로 사용하는 소스와 빌드를 구분한다. 개발 체크아웃의
`npm run build` 성공은 다른 호스트의 배포나 실행 중인 프로세스의 재시작을
의미하지 않는다. 생성된 런타임 manifest는 대상 확인 모듈과 승인 재개 모듈도
추적한다.

문제가 생기면 다음을 확인한다.

1. 시작 로그의 hub 주소, 역할과 작업 폴더가 의도한 설정인지 확인한다.
2. 실행기 목록에서 연결 규약, 인스턴스와 프로젝트 경로를 확인한다.
3. 해당 프로젝트가 로컬인지 특정 worker로 지정되어 있는지 확인한다.
4. worker가 재시작되었거나 프로젝트 경로가 바뀌었다면 이전 대기 작업을
   그대로 재개하지 말고 새 대상으로 다시 요청한다.

이 검사는 실행 위치 혼동을 막기 위한 것이다. OS 프로세스 샌드박스,
이미 실행 중인 외부 프로세스의 강제 취소, 모델 대화의 자동 재개를 제공하지는
않는다.
