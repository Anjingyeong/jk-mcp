# JK 사용 가이드

JK는 도구 이름을 외워서 쓰는 프로그램이 아닙니다. **ChatGPT에 자연어로 개발 목표를 말하면, JK가 로컬 프로젝트 접근·수정·검증을 담당하는 방식**이 기본입니다.

대부분의 사용자는 아래 6개 패턴만 알면 충분합니다.

## 1. 가장 쉬운 사용법

기본 공식은 다음과 같습니다.

```text
@jk [프로젝트]에서 [하고 싶은 일]. [중요한 제약]. [어떻게 검증할지]. [마무리 작업].
```

예:

```text
@jk chatgpt2codex에서 이 버그 원인 찾아서 고치고 typecheck랑 관련 테스트까지 해줘.
```

프로젝트가 대화 문맥상 명확하면 이름도 생략할 수 있습니다.

```text
@jk 이 버그 고치고 테스트까지 해줘.
```

JK가 정상 연결되어 있으면 ChatGPT는 보통 내부적으로 프로젝트를 선택하고, 필요한 코드를 읽고, 수정하고, 가장 가까운 검증을 실행합니다.

## 2. 자주 쓰는 6가지 패턴

### A. 프로젝트 분석만 하기

코드는 바꾸지 않고 구조나 문제를 파악하고 싶을 때:

```text
@jk 이 프로젝트 구조 뜯어보고 어떻게 작동하는지 설명해줘. 수정은 하지 마.
```

```text
@jk 성능 병목 후보를 코드 근거로 찾아줘. 아직 수정하지 마.
```

### B. 기능 구현하기

```text
@jk 로그인 실패 로그를 사용자에게 보여주는 기능 추가하고 typecheck랑 관련 테스트까지 해줘.
```

완료 조건이 있으면 같이 말하는 것이 좋습니다.

```text
@jk 검색 결과에 로딩 상태를 추가해줘. 기존 UI 스타일은 유지하고, 모바일에서도 깨지지 않게 하고, 테스트까지 통과시켜줘.
```

### C. 버그 디버깅하기

```text
@jk 이 에러 원인부터 코드로 확인해서 고쳐줘. 같은 수정 반복하지 말고 실패하면 다른 가설로 전환해.
```

JK 네이티브 루프에는 실패 복구 규칙이 있으므로, 긴 디버깅 작업에서는 원인 확인 -> 수정 -> 검증 -> 실패 분석을 반복할 수 있습니다.

### D. 이전 작업 이어가기

```text
@jk 아까 chatgpt2codex에서 하던 project_rules 작업 이어서 마무리해줘.
```

```text
@jk 아까 작업 이어서 테스트하고 README까지 정리해줘.
```

같은 저장소에서 여러 작업을 동시에 했다면 **프로젝트 이름 + 작업 주제**를 같이 말하면 잘못된 세션을 이어갈 가능성이 줄어듭니다.

```text
@jk developer-portfolio에서 어제 하던 VLM 설명 수정 작업 이어서 해줘.
```

사용자가 `workSessionId`를 직접 기억할 필요는 없습니다. 이것은 JK 내부의 작업 흐름 분리용 식별자입니다.

### E. E2E와 스크린샷까지 확인하기

```text
@jk e2e 테스트하고 스크린샷 보여줘.
```

웹 프로젝트라면 환경에 따라 데스크톱/모바일 화면, 브라우저 콘솔 오류, 실패한 네트워크 요청까지 확인할 수 있습니다.

UI 변경 후에는 다음처럼 요청하면 좋습니다.

```text
@jk 수정한 화면 e2e로 확인하고 데스크톱/모바일 스크린샷까지 보여줘. 문제 있으면 고치고 다시 검증해.
```

### F. Git 커밋 / 푸시하기

JK는 commit이나 push를 자동으로 해버리는 것보다 **사용자가 명시적으로 요청했을 때 수행하는 방식**을 사용합니다.

```text
@jk 변경사항 diff 검토하고 문제 없으면 커밋해줘.
```

```text
@jk 테스트 통과 확인하고 커밋한 다음 jk-mcp에 푸시해줘.
```

단순히 "고쳐줘"라고 말한 경우에는 보통 수정과 검증까지만 기대하는 것이 안전합니다.

### G. Local / Remote 실행 선택

프로젝트는 기본적으로 **local-only**입니다. Remote executor는 사용자가 별도로 연결하고 해당 작업에서 선택했을 때만 사용합니다.

여러 executor가 같은 Git 프로젝트를 공유한다면 configured upstream을 durable source of truth로 사용합니다.

- 일반 작업과 해당 PC에만 있는 파일·도구는 local executor에서 처리합니다.
- 다른 연결 머신을 의도적으로 사용할 때만 remote executor를 선택합니다.
- 공유 remote checkout은 작업 전에 clean 상태와 fast-forward-only upstream 동기화를 확인합니다.
- dirty/diverged/local-only commit을 stash/reset/rebase/force로 자동 정리하지 않습니다.
- Windows는 자동 pull하지 않습니다. 사용자가 명시적으로 요청했을 때만 수동 동기화합니다.
- 같은 branch를 여러 executor에서 독립적으로 동시에 수정하지 않습니다.
- 공개 JK는 특정 클라우드 공급자나 기본 배포 서버를 전제로 하지 않습니다.

## 3. 추천 프롬프트 구조

긴 작업일수록 다음 네 가지를 넣으면 결과가 안정적입니다.

```text
1. 프로젝트
2. 목표
3. 제약 / 하지 말아야 할 것
4. 검증 및 마무리 조건
```

예:

```text
@jk chatgpt2codex에서 README 사용법을 정리해줘.
기존 기술 설명은 유지하고 사용자가 바로 복붙할 수 있는 예제를 우선해.
내부 구현 설명을 너무 늘리지 말고 오버프로그래밍도 피하고,
typecheck/build 확인 후 변경사항을 요약해줘. 커밋은 하지 마.
```

## 4. 기본 사용자와 고급 사용자의 차이

### 기본 사용자: 도구 이름을 몰라도 됨

다음은 직접 호출할 필요가 거의 없습니다.

- `goal_intake`
- `goal_loop`
- `project_select`
- `session_resume`
- `workSessionId`
- 파일 해시 / patch precondition
- checkpoint ID

그냥 원하는 결과를 자연어로 요청하는 편이 좋습니다.

### 고급 사용자: 동작을 통제하고 싶을 때

특정 방식을 강제하고 싶다면 자연어로 명시하면 됩니다.

```text
@jk 먼저 분석만 하고 수정은 하지 마.
```

```text
@jk 작은 단위로 수정하고 매 단계마다 테스트해.
```

```text
@jk 기존 변경사항은 건드리지 말고 이 파일 범위만 수정해.
```

```text
@jk 실패하면 같은 패치를 반복하지 말고 원인을 다시 확인해.
```

```text
@jk 완료라고 하기 전에 typecheck, 관련 테스트, build를 확인해.
```

## 5. `goal_intake`와 `goal_loop`는 언제 쓰이나

보통 사용자가 직접 호출하는 기능은 아닙니다.

큰 작업이 들어오면 ChatGPT가 JK를 통해 대략 다음 순서로 움직입니다.

```text
goal_intake / goal_loop
  -> 프로젝트 선택
  -> 규칙 / 상태 확인
  -> 코드 검색 및 좁은 범위 읽기
  -> 수정
  -> typecheck / test / build / E2E 중 필요한 검증
  -> 실패 시 원인 재검토
  -> 완료 또는 실제 blocker 보고
```

즉 `goal_loop`의 목적은 별도 AI 모델을 호출하는 것이 아니라 **현재 ChatGPT 웹 세션이 작업을 중간에 놓치지 않고 inspect -> edit -> verify 루프를 유지하도록 돕는 것**입니다.

## 6. 저장소 규칙: `AGENTS.md` / `CLAUDE.md`

프로젝트에 지속적으로 적용하고 싶은 규칙은 대화마다 반복해서 말하는 대신 저장소에 둘 수 있습니다.

예:

```text
project/
  AGENTS.md
  src/
    AGENTS.md
    auth/
      CLAUDE.md
      login.ts
```

`src/auth/login.ts`를 작업할 때 JK는 경로 기준 규칙을 읽을 수 있습니다.

```text
project/.codex/config.toml
project/AGENTS.md
project/src/AGENTS.md
project/src/auth/CLAUDE.md
```

규칙은 루트에서 작업 위치 방향으로 반환되므로, 저장소 전체 규칙과 특정 하위 영역 규칙을 분리하기 쉽습니다.

추천 용도:

```markdown
# AGENTS.md
- TypeScript strict mode를 유지한다.
- 기존 public API를 임의로 깨지 않는다.
- 수정 후 관련 테스트와 typecheck를 실행한다.
```

하위 폴더에는 그 영역에서만 필요한 규칙을 둡니다.

```markdown
# src/auth/AGENTS.md
- 인증 실패 원인을 로그에 남기되 토큰 값은 출력하지 않는다.
- auth 관련 변경은 auth 테스트를 반드시 실행한다.
```

## 7. OMO는 언제 쓰면 되나

기본 JK 작업에는 OMO가 필요하지 않습니다.

그냥:

```text
@jk 이 기능 구현해줘.
```

라고 하면 JK 네이티브 루프를 사용하는 것이 기본입니다.

OMO를 별도 로컬 에이전트 런타임으로 사용하고 싶을 때만 명시합니다.

```text
@jk OMO로 이 프로젝트 구조를 한 번 더 분석해줘.
```

OMO는 자체 provider 인증과 런타임 상태에 영향을 받으므로, **일상 작업에서는 JK 네이티브를 기본값으로 두는 것이 단순합니다.**

## 8. 실전 치트시트

| 하고 싶은 일 | 이렇게 말하기 |
| --- | --- |
| 구조 이해 | `@jk 이 프로젝트 뜯어서 작동 원리 설명해줘. 수정은 하지 마.` |
| 기능 구현 | `@jk 이 기능 추가하고 관련 테스트까지 해줘.` |
| 버그 수정 | `@jk 원인부터 확인해서 고치고 재현 테스트까지 해줘.` |
| 이어서 작업 | `@jk 아까 [프로젝트/작업 주제] 하던 거 이어서 해줘.` |
| UI 검증 | `@jk e2e 테스트하고 데스크톱/모바일 스크린샷 보여줘.` |
| 리뷰 | `@jk 현재 diff 리뷰해서 회귀 위험이나 빠진 검증 찾아줘.` |
| 커밋 | `@jk 검증 통과하면 변경사항 리뷰 후 커밋해줘.` |
| 푸시 | `@jk 검증하고 커밋한 다음 [remote]에 푸시해줘.` |
| 규칙 적용 | 프로젝트/하위 폴더에 `AGENTS.md` 작성 |
| OMO 사용 | `@jk OMO로 ... 해줘.`라고 명시 |

## 9. 굳이 신경 쓰지 않아도 되는 것

JK를 잘 쓰기 위해 다음을 매번 생각할 필요는 없습니다.

- 어떤 tool을 먼저 호출할지
- lease ID가 무엇인지
- loop ID가 무엇인지
- 현재 파일 SHA-256이 무엇인지
- checkpoint를 언제 만들지
- 어떤 테스트 명령을 선택할지

이것들은 JK와 ChatGPT가 처리해야 할 실행 세부사항입니다.

사용자가 신경 써야 하는 것은 주로 세 가지입니다.

```text
무엇을 원하는가?
무엇을 건드리면 안 되는가?
어떤 상태가 되면 완료인가?
```

이 세 가지가 명확하면 JK를 가장 효율적으로 사용할 수 있습니다.
